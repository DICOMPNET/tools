🔮 Inference Throughput Estimator

Estimate inference throughput in tokens per second from the generated token count and end-to-end latency, for capacity planning.

📐 計算公式 / 原理
推理總吞吐（本頁程式碼口徑）：單請求時延=TTFT+（生成 tokens−1）×TPOT；總吞吐=tokens×併發批次÷單請求時延（tokens/s）；單請求吞吐=tokens÷單請求時延。校驗：空值按 0 兜底，TTFT 可為 0，TPOT 或併發為 0 時結果非有限並追加警示「部分結果無定義」。判據：無固定分級，總吞吐衡量服務整體利用率，結果保留 1 位小數、非有限時顯示 —。
推理服務的核心指標：總吞吐衡量叢集利用率，單請求吞吐才是使用者感知的快慢。本頁把端到端時延拆成「首 token 延遲 TTFT」與「每 token 間隔 TPOT」兩段：TTFT 反映預填充與排隊，TPOT 反映解碼速度；總時延=TTFT+(tokens−1)×TPOT。實際 batching 會拉長 TTFT/TPOT 並受頻寬瓶頸限制，請用實測兩段時延複核，再按 SLO 取捨。

📐 計算公式與說明

單請求吞吐與時延（本頁程式碼口徑，與上方總吞吐互補）：單請求時延=TTFT+（生成 tokens−1）×TPOT；單請求吞吐=生成 tokens÷單請求時延（tokens/s）；平均每 token 毫秒=單請求時延×1000÷生成 tokens；純解碼速度≈1000÷TPOT（ms/token）。校驗：與總吞吐共用同一組輸入，TPOT 或併發為 0 時該項無定義並同樣觸發警示。判據：本頁不建模 batching 對 TTFT/TPOT 的拉長；實際容量規劃須用實測 TTFT、TPOT 與頻寬拐點複核。

實際受批大小與排隊影響。

📚 深度解析：推理吞吐估算

💡 常見使用場景

  • 吞吐≈生成 token 數 / 端到端時延(tokens/s)，衡量服務處理速度。
  • 受模型大小、批大小、KV 快取與硬體頻寬共同影響，非僅由 FLOPs 決定。
  • 容量規劃用 吞吐×併發上限 估算峰值 QPS，需預留餘量防雪崩。
單請求吞吐
生成 200 token 耗時 4s → 吞吐=50 tokens/s。若單卡支援 4 併發且各 50 tok/s，總吞吐≈200 tok/s；但實際共享 KV 快取與頻寬，併發增益低於線性。

❓ 常見問題（FAQ）

為什麼吞吐不隨併發線性增長？
視訊記憶體頻寬與算力是共享瓶頸，多請求競爭 KV 快取與計算單元，邊際吞吐遞減；需實測找到拐點再定併發上限。
首 token 延遲和吞吐衝突嗎？
常衝突。大模型首 token 受預填充耗時影響，吞吐受解碼並行影響；最佳化方向相反時按業務(對話要低延遲、批處理要高吞吐)取捨。
